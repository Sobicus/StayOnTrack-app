Как это работает
1️⃣ Ты говоришь голосом 🎤
2️⃣ Приложение переводит речь в текст
3️⃣ Текст отправляется мне как сообщение
4️⃣ Я отвечаю на него так же, как на обычный текстовый вопрос

То есть для меня разницы нет:

❌ печатал ты сообщение

✅ или надиктовал голосом

Я получаю уже текст.

3.2. Почему это лучше, чем жёсткая таблица
✅ Учитывает вес пользователя
✅ Масштабируется на сотни активностей
✅ Не надо хранить отдельные таблицы для 60 кг / 75 кг / 95 кг
✅ Можно легко добавить новые упражнения

3.3. Архитектура данных
Таблица activities
type ActivityUnit = 'minute' | 'rep' | 'meter' | 'step';

interface Activity {
  id: string;
  slug: string;
  name: string;
  unit: ActivityUnit;
  met?: number;              // для длительных активностей
  caloriesPerRepBase?: number; // для повторений, если не считаем через MET
  defaultWeightKg?: number;  // например 75
  category: string;
  icon?: string;
}
3.4. Как считать для минутных активностей
function caloriesPerMinute(met: number, weightKg: number): number {
  return (met * 3.5 * weightKg) / 200;
}
3.5. Как считать для повторений
Для повторений есть 2 варианта:

Вариант A — простой для MVP
Хранить фиксированную цену повтора:

const pushup = 0.5; // kcal per rep for ~75kg
И масштабировать по весу:

function caloriesPerRep(baseCalories: number, weightKg: number, baseWeightKg = 75) {
  return baseCalories * (weightKg / baseWeightKg);
}
Вариант B — более правильный
Хранить:

среднюю длительность 1 повтора

MET упражнения

Но для MVP это уже лишнее.

3.6. Перевод “сэкономленных калорий” в эквивалент
function activityEquivalent(savedCalories: number, caloriesPerUnit: number): number {
  return savedCalories / caloriesPerUnit;
}
Пример:

const saved = 500;
const runningPerMinute = 10;

const runningMinutes = saved / runningPerMinute; // 50 минут

Ты сохранил себе усилие, время и здоровье.

То есть приложение должно продавать не наказание, а осознанную выгоду.

❌ Плохой тон:
“Ты опять чуть не сорвался.”

✅ Хороший тон:
“Сегодня ты сохранил 420 kcal — это как минус 42 минуты бега.”

1. Идея с переводом калорий в лишний вес / несброшенный вес — да, можно ✅
Но тут важно показать это аккуратно и честно.

Базовая логика
Часто используют приближение:

~7 700 kcal ≈ 1 кг жировой массы

или

~3 500 kcal ≈ 1 фунт (~0.45 кг)

Но это не точная математика 1-в-1, потому что реальное изменение веса зависит от метаболизма, воды, состава тела, активности и других факторов. Даже Mayo Clinic отдельно подчёркивает, что это упрощённая модель, а не идеальный предсказатель. 

Как это лучше показывать в приложении
❌ Плохо:

“Ты точно похудел на 0.8 кг”

✅ Лучше:

“Ты создал дефицит, эквивалентный примерно 0.8 кг потенциально не набранного жира”

или

“Ты избежал калорий, которые примерно соответствуют 0.8 кг лишнего веса”

или

“Это приблизительный эквивалент 0.8 кг жирового запаса, если смотреть только по калориям”

Формула для MVP
const FAT_KG_EQUIVALENT = savedCalories / 7700;
Примеры
500 kcal = ~0.065 кг

2 000 kcal = ~0.26 кг

7 700 kcal = ~1 кг

15 400 kcal = ~2 кг

Вот хорошие варианты:

На русском:

  challengeParticipants ChallengeParticipant[]

8. Логика расчётов
Saved calories
savedCalories = caloriesPerOccurrence * (1 - portionRatio)
Примеры:
avoided → portionRatio = 0

consumed → portionRatio = 1

half eaten → portionRatio = 0.5

Saved money
savedMoney = pricePerOccurrence * (1 - portionRatio)
Potential weight avoided
potentialWeightAvoidedKg = totalSavedCalories / 7700
⚠️ Показывать как approximate, а не как точный прогноз.

Equivalent activity
units = savedCalories / caloriesPerUnit
Пример:

500 / 10 = 50 minutes of running
Streak logic
Я бы рекомендовал считать streak так:

день считается успешным, если по всем активным привычкам за день есть:

avoided

или partial, если ты хочешь partial считать допустимым

Можно сделать настройку:

Вариант A
partial = success

Вариант B
partial = neutral

Вариант C
partial = fail only if ratio > 0.8

Для MVP я бы взял:

✅ avoided = success
✅ partial = success if portionRatio <= 0.5
❌ consumed = fail

2. TypeORM или Prisma
Мой честный вывод:
Если тебе нужно быстро и удобно стартовать именно тебе — TypeORM нормальный выбор.
Почему я так думаю:

✅ Почему TypeORM здесь подходит
Ты уже с ним работал
У тебя уже есть опыт с NestJS + TypeORM, а это огромный плюс.
В MVP скорость разработки почти всегда важнее “идеальной теории”.

Он хорошо ложится на NestJS-архитектуру
TypeORM строится вокруг Entity-классов, репозиториев и связей, что естественно сочетается с Nest-модулями. 

Можно делать нормальную доменную модель
Для твоего продукта сущности типа User, Habit, HabitLog, Challenge, Friendship будут выглядеть очень естественно именно через entity-based подход. 

TypeORM поддерживает Data Mapper и Active Record
Но для твоего случая я бы советовал именно Data Mapper style, а не Active Record. Это лучше для роста проекта. 

Когда я бы выбрал Prisma вместо TypeORM
Prisma я бы выбирал, если бы ты хотел:

максимум DX и type-safety на уровне клиента

очень быстро делать CRUD и простые запросы

проще и понятнее вести миграции через Prisma Migrate

меньше возиться с ORM-магией и decorators

Prisma официально делает сильный упор на type-safe client и migrations. 

Но в твоём случае я всё равно склоняюсь к TypeORM
Потому что у тебя уже есть:

опыт с NestJS

опыт с TypeORM

понимание entity/repository-подхода

привычка к более “backend-style” архитектуре

То есть здесь цена переключения на Prisma может быть просто не нужна.

3. Монорепозиторий или микросервисы
✅ Для этого продукта я бы точно не начинал с микросервисов
Причина очень простая:

У тебя сейчас продуктовый риск, а не инфраструктурный
Главный вопрос сейчас не:

“Сможет ли система выдержать 10 миллионов пользователей?”

Главный вопрос:

“Нужен ли людям вообще такой продукт, будут ли они пользоваться, возвращаться, звать друзей и проходить челленджи?”

Для такой стадии микросервисы обычно только:

замедляют старт

усложняют отладку

увеличивают количество инфраструктурных проблем

добавляют оверхед на коммуникацию между сервисами

Nest официально описывает микросервис как отдельное приложение с другим transport layer, а не просто “чуть более модульный backend”. 

Почему монолит лучше для MVP
✅ Плюсы
Быстрее сделать

Проще дебажить

Проще деплоить

Проще менять модель данных

Проще делать транзакции

Проще запускать одному разработчику или маленькой командой

Для продукта с сущностями:

users

habits

logs

friends

challenges

leaderboards

всё это спокойно живёт в одном приложении.

4. А монорепозиторий нужен?
Да, монорепо я бы взял
Но тут важно различать:

монорепозиторий ≠ микросервисы
Можно сделать:

один backend

один web frontend

один mobile app

shared types / shared DTO / shared constants

и всё это держать в одном monorepo.

Nest CLI отдельно поддерживает monorepo mode и libraries для шаринга компонентов между приложениями. 

Для твоего проекта монорепо особенно удобно, если будет:
apps/api

apps/web

apps/mobile

libs/shared-types

libs/ui-contracts

libs/utils

Это очень удобно, если ты хочешь:

общий enum HabitCategory

общие DTO

общие response types

общие правила валидации

единые constants для leaderboard/challenge logic

6. Когда уже думать о микросервисах
Я бы начал думать о выделении сервисов только если появится хотя бы один из этих признаков:

1.
Один домен начинает жить сильно отдельно
Например, challenges/social вырастают в отдельную сложную подсистему.

2.
Нужны разные нагрузки и scaling patterns
Например:

stats/leaderboards очень тяжёлые

social notifications идут отдельно

analytics считается пачками

3.
Появляется команда из нескольких разработчиков, и они реально мешают друг другу

4.
Появляются фоновые heavy jobs:

пересчёт leaderboard

anti-cheat

weekly summaries

recommendation engine

push campaigns

Тогда уже можно выделять:

social-service

challenge-service

stats-service

notifications-service

Но не в первой версии.

7. Что я бы сделал на твоём месте конкретно
Мой совет:
✅ Бери TypeORM
если:

хочешь стартовать быстрее

хочешь использовать знакомый стек

хочешь entity/repository style

не хочешь сейчас переключаться на Prisma

✅ Бери монорепозиторий
если:

планируешь web + mobile + api

хочешь shared types

хочешь один source of truth

❌ Не бери сейчас микросервисы
потому что для этой идеи это почти наверняка будет ранним переусложнением.

выносить leaderboards/statistics

Для тебя сейчас:

А с монорепо если надо будет на микросервисы легко перейти?

Да, с монорепо перейти на микросервисы обычно легче, чем из хаотичного single-repo или из нескольких несвязанных репозиториев ✅
Но тут есть важная оговорка:

Монорепо само по себе не делает переход “автоматически лёгким”
Лёгкость перехода зависит не столько от monorepo, сколько от того, как ты изначально построишь монолит.

1. Когда переход действительно будет легче
Если ты изначально делаешь не просто “один большой ком грязи”, а modular monolith, тогда потом можно относительно спокойно вырезать модули в отдельные сервисы.

То есть внутри NestJS у тебя уже есть, например:

auth

users

habits

habit-logs

stats

friends

challenges

leaderboards

notifications

Если каждый модуль:

имеет свои сервисы

имеет свои DTO

имеет свои use-cases

не лезет напрямую во внутренности других модулей

общается через понятные интерфейсы

тогда потом можно сказать:

“Окей, notifications выносим отдельно”
“Окей, leaderboards выносим отдельно”

И это будет реально проще.

2. Что именно даёт монорепо
✅ Плюсы monorepo для будущего перехода
1. Общие типы и контракты
Ты можешь иметь:

libs/contracts

libs/shared-types

libs/common

libs/utils

И когда выносишь сервис, не нужно заново копировать типы.

2. Общая кодовая база
В одном месте лежат:

backend

frontend

shared libs

later microservices

Например:

apps/
  api
  web
  mobile
  notifications-service
  stats-service

libs/
  contracts
  common
  utils
  auth
То есть ты можешь добавлять новые сервисы постепенно, не ломая всё.

3. Проще рефакторить
Когда проект в одном monorepo:

проще двигать код

проще выделять shared contracts

проще искать зависимости

проще управлять version consistency

3. Но есть важный риск
❌ Если изначально сделать сильную связанность модулей, monorepo не спасёт
Например, если у тебя:

ChallengeService напрямую лазит в HabitRepository

StatsService дергает полпроекта

FriendsService знает слишком много про UsersService

все модули используют одни и те же entity без границ

тогда при выносе в микросервисы начнётся боль:

циклические зависимости

поломанные импорты

shared business logic размазана по проекту

много sync-запросов между будущими сервисами

4. Как строить сейчас, чтобы потом было легко вынести
Вот это самое важное 🔴

Строй не “монолит”, а modular monolith
Правило 1. У каждого домена — свой модуль
Например:

AuthModule

UsersModule

HabitsModule

HabitLogsModule

StatsModule

FriendsModule

ChallengesModule

Правило 2. Не давай модулям лазить в чужие репозитории напрямую
❌ Плохо:

ChallengesService напрямую использует HabitLogsRepository

✅ Лучше:
ChallengesService использует HabitLogsFacade или HabitLogsQueryService

То есть доступ через публичный API модуля, а не напрямую в кишки.

Правило 3. Shared — только для общего, а не для всего подряд
Очень частая ошибка:

libs/shared
и туда складывают вообще всё подряд.

Лучше разделять:

libs/common
libs/contracts
libs/config
libs/database
И не пихать туда доменную бизнес-логику.

Правило 4. Доменные правила держать внутри модуля
Например:
логика streak должна жить либо в:

habit-logs

либо stats

но не быть размазанной по контроллерам, утилям и random helper files.

Правило 5. Сразу думать, где будут будущие кандидаты на вынос
Для твоего проекта потенциальные кандидаты на будущие микросервисы:

1. notifications
push, email, reminders

2. stats / analytics
heavy recalculation, aggregates, snapshots

3. leaderboards
отдельные ranking jobs, anti-cheat, cached views

4. social / challenges
если social-часть сильно вырастет

5. Где монорепо особенно удобно при миграции
Допустим, сначала у тебя так:

apps/
  api

libs/
  common
  contracts
Потом выросла нагрузка на notifications.

Ты добавляешь:

apps/
  api
  notifications-service
И сначала можешь даже оставить часть логики в монолите, а часть уже вынести.
То есть переход можно делать постепенно, а не “переписать всё за ночь”.

Это большой плюс.

8. На что обратить внимание, чтобы не сломать себе будущее
Делай так:
✅ модули с чёткими границами
✅ минимум прямых межмодульных зависимостей
✅ DTO/контракты отдельно
✅ инфраструктурный код отдельно
✅ бизнес-логику не размазывать
✅ не использовать одну giant shared папку для всего мира

Не делай так:
❌ все сервисы знают обо всём
❌ одна общая mega-entity model на весь проект без границ
❌ общие helper-утилиты с бизнес-логикой
❌ прямой доступ в чужие repositories
❌ завязка всего на sync-calls между доменами

Каждый модуль должен иметь свой публичный API

19. Как подготовить проект к будущему выносу в микросервисы
Вот самые важные правила.

✅ Правило 1. Не использовать чужие repositories напрямую
Общение между модулями — через сервисы/фасады.

✅ Правило 2. У каждого модуля свои сущности и таблицы
Даже если физически база одна.

✅ Правило 3. Минимизировать bidirectional dependencies
Модуль A знает про публичный API модуля B, но не наоборот, если это не нужно.

✅ Правило 4. Не класть бизнес-логику в controllers
Контроллер только принимает запрос и передаёт в application service.

✅ Правило 5. Отдельно держать background jobs
Например, weekly summary или leaderboard recalculation.

Сейчас они могут быть в монолите, но лучше уже держать их в отдельной зоне.

25. Самый короткий итог
✅ Да, вот как лучше строить:
Monorepo → modular monolith → потом при необходимости workers → потом микросервисы

✅ Структура:
apps — приложения

libs/modules — домены

libs/contracts — контракты

libs/database — infra DB

libs/config — конфиги

✅ Главное правило:
Строй так, чтобы каждый модуль был почти как маленький самостоятельный сервис, даже если сейчас он живёт внутри монолита.
